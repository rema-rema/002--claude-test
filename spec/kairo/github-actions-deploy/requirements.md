# GitHub Actions 自動デプロイシステム 要件定義書

## 1. プロジェクト概要

### 1.1 目的
既存の手動デプロイプロセスを GitHub Actions を使った自動化システムに置き換え、開発効率の向上とデプロイミスの削減を実現する。

### 1.2 背景
- 現在: 手動でビルド・デプロイ・サーバー再起動を実行
- 問題: 手順の複雑化、ヒューマンエラーリスク、時間コスト
- 解決策: GitHub リポジトリへのプッシュで自動的にビルド・テスト・デプロイを実行

### 1.3 対象システム
- **既存環境**: `/home/rema/release/002--claude-test/`
- **フロントエンド**: Next.js (port 3001)
- **バックエンド**: FastAPI (port 8000) 
- **リバースプロキシ**: nginx (`http://home.poco`)
- **テストフレームワーク**: Playwright

## 2. 機能要件

### 2.1 自動ビルドシステム
**要件**: コードプッシュ時の自動ビルド実行
- Next.js プロジェクトの `npm run build` 自動実行
- Python 依存関係の自動インストール・検証
- ビルド成果物の品質チェック
- ビルド失敗時の通知機能

**成功条件**: 
- ビルドエラーがない状態でビルド成果物が生成される
- ビルド時間が 5分以内で完了する

### 2.2 自動テストシステム  
**要件**: デプロイ前の自動テスト実行
- Playwright E2E テストの自動実行
- テスト失敗時のデプロイ停止機能
- テスト結果レポートの自動生成
- スクリーンショット・動画キャプチャの保存

**成功条件**:
- 全てのテストが通過した場合のみデプロイを継続
- テスト実行時間が 10分以内で完了する

### 2.3 自動デプロイシステム
**要件**: テスト通過後の自動デプロイ実行
- SSH経由でのサーバー接続・ファイル転送
- 既存サーバープロセスの安全な停止・起動
- デプロイ完了後のヘルスチェック実行
- ロールバック機能（デプロイ失敗時）

**成功条件**:
- デプロイ後に `http://home.poco` で正常アクセス可能
- Step 1-6 ログインフローが正常動作する

### 2.4 環境別デプロイ
**要件**: ブランチに応じた環境別デプロイ
- `develop` ブランチ → ステージング環境 (`/home/rema/release/002--claude-test/`)
- `main` ブランチ → 本番環境（将来的に別ディレクトリ）
- Pull Request → テスト結果のコメント投稿

### 2.5 通知システム
**要件**: デプロイ状況の自動通知
- ビルド・テスト・デプロイの各段階での状況通知
- 成功・失敗の結果通知
- エラー詳細の報告（ログ・スクリーンショット含む）

## 3. 非機能要件

### 3.1 セキュリティ要件
- SSH秘密鍵の安全な管理（GitHub Secrets使用）
- 環境変数の暗号化保存
- デプロイ権限の制限（特定ブランチのみ）
- サーバーアクセスの監査ログ記録

### 3.2 可用性要件
- デプロイ失敗時の自動ロールバック機能
- サーバーダウンタイムの最小化（ゼロダウンタイムデプロイ）
- GitHub Actions 実行時間制限内での処理完了

### 3.3 保守性要件
- デプロイスクリプトの可読性・保守性確保
- 設定変更の容易性
- ログの適切な出力・保存

## 4. 制約事項

### 4.1 できること
- **ビルド自動化**: Next.js, Python依存関係
- **テスト自動化**: Playwright E2E テスト実行
- **ファイル配置**: SSH/rsync によるファイル転送
- **プロセス管理**: systemctl によるサービス再起動
- **ヘルスチェック**: HTTP API によるサーバー状態確認

### 4.2 できないこと・事前準備が必要
- **システム設定変更**: nginx, dnsmasq, systemd の初期設定
- **権限設定**: sudo 権限が必要な操作
- **SSL証明書**: HTTPS 関連の設定変更
- **DNS変更**: ドメイン設定の変更

### 4.3 前提条件
- サーバーのSSHアクセス環境が設定済み
- 必要なサービス（nginx, systemd）が既に設定済み  
- GitHub リポジトリへのアクセス権限

## 5. 成功指標・検証方法

### 5.1 機能検証
- [ ] コードプッシュから5分以内でビルド完了
- [ ] 全Playwrightテストが10分以内で完了・通過
- [ ] デプロイ後に `http://home.poco` で正常アクセス確認
- [ ] Step 1-6 ログインフローの自動テスト成功
- [ ] デプロイ失敗時の自動ロールバック動作確認

### 5.2 運用検証
- [ ] 1週間の連続運用でエラー発生率 5% 以下
- [ ] デプロイ作業時間の 80% 以上削減
- [ ] 手動作業ミスの発生率 0%

## 6. 実装優先度

### Phase 1: コア機能 (必須)
1. 自動ビルドシステム
2. 自動テストシステム  
3. 基本的なデプロイ機能

### Phase 2: 運用改善 (重要)
1. 環境別デプロイ
2. ロールバック機能
3. 通知システム

### Phase 3: 拡張機能 (オプション)
1. 高度な監視・アラート
2. デプロイメトリクス収集
3. 複数環境対応

## 7. リスクと対策

### 7.1 技術リスク
- **SSH接続失敗**: 複数接続試行・タイムアウト設定
- **ビルド失敗**: 詳細ログ・エラー通知
- **テスト不安定**: リトライ機能・並列実行制限

### 7.2 運用リスク  
- **デプロイ失敗**: 自動ロールバック・手動介入手順
- **サービス停止**: ヘルスチェック・段階的デプロイ
- **セキュリティ**: 秘密鍵管理・アクセス制御
